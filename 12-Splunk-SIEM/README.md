# Splunk SIEM & Security Log Analysis Lab

## Overview

Hands-on Splunk exercises completed during EC-Council Certified SOC Analyst (CSA) training in controlled virtual lab environments.

The sessions focused on data ingestion, log forwarding, SPL-based investigation, authentication analysis, web log analysis, detection alerts, dashboards, knowledge objects, threat-intelligence enrichment, and workflow automation.

## Objectives

- Understand Splunk SIEM and its data pipeline
- Ingest security logs into Splunk
- Configure different log-ingestion methods
- Analyze Linux, Apache, SSH, Windows, and firewall logs
- Perform SPL-based investigations
- Identify suspicious authentication activity
- Investigate web application activity
- Create detection alerts
- Build dashboards and reports
- Use Splunk knowledge objects
- Perform IP reputation analysis
- Integrate threat-intelligence workflow actions

## Lab Environment

The exercises were performed in controlled virtual lab environments using Splunk, Ubuntu, Kali Linux, Windows, and Apache web services.

---

## Splunk Data Ingestion

Practiced multiple methods of getting security data into Splunk.

### 1. Log File Upload

Uploaded an Apache `access.log` file into Splunk.

Configured:

- Sourcetype
- Index
- Log source

The imported Apache events were then searched and analyzed using SPL.

### 2. TCP/UDP Data Ingestion

Configured Splunk to monitor network data through TCP/UDP port `3030`.

Netcat was used to generate test data for ingestion.

### 3. Splunk Forwarder

Configured a Splunk Forwarder on Kali Linux to send logs to the Splunk server.

Apache activity was generated on Kali and the resulting web-server logs were forwarded to Splunk.

### 4. Windows Log Ingestion

Practiced forwarding and analyzing Windows system and firewall logs.

Also worked with uploaded Windows access, authentication, and error logs.

## SPL Practice

Practiced SPL commands and search techniques.

### Basic Searches

```spl
index=*
```

```spl
index="uplogs"
```

### Display Fields

```spl
index="uplogs" | table clientip
```

```spl
index="uplogs" | table clientip,method,status
```

```spl
index="uplogs" | table clientip,file,useragent
```

### Deduplication

```spl
index="uplogs" | table clientip | dedup clientip
```

### Statistics

```spl
index="uplogs" | table clientip | stats count by clientip
```

### Top and Rare Values

```spl
index="uplogs" | table clientip | top clientip
```

```spl
index="uplogs" | table clientip | rare clientip
```

### Event Limits

```spl
index="uplogs" | table clientip | head
```

```spl
index="uplogs" | table clientip | tail
```

## HTTP Log Analysis

Analyzed Apache access logs to investigate web activity.

Practiced identifying:

- Client IP addresses
- Requested files
- HTTP methods
- HTTP status codes
- User-agent information

Example search:

```spl
index="uplogs" method=GET
```

Used statistics to identify the number of GET requests generated by individual client IP addresses.

---

## HTTP Status Code Investigation

Analyzed successful and unsuccessful HTTP requests.

Example:

```spl
index="uplogs"
| table clientip,file,method,status
| where status="200" AND method="GET"
| dedup clientip
```

Also investigated HTTP `404` responses to identify potential directory-enumeration or other suspicious web activity.

---

## SSH Authentication Analysis

Investigated Linux authentication logs to identify suspicious SSH activity.

Example:

```spl
index="ublogs" source="var/log/auth.log"
```

Searched for failed authentication activity using:

```spl
"Failed" AND "password"
```

Also investigated:

```spl
"invalid" AND "user"
```

Fields such as usernames and attacker IP addresses were extracted and analyzed.

This helped identify repeated authentication failures and invalid-user activity.

## Apache Directory Brute-Force Detection

Generated controlled directory-enumeration activity against a lab Apache server.

Created a search for repeated HTTP `404` responses:

```spl
index=* source="/var/log/apache2/access.log" "404" AND "GET"
```

The resulting events were analyzed to identify the source IP generating the requests.

A Splunk alert was created from this detection logic.

---

## XSS Detection

Performed a controlled cross-site scripting test against a lab web application.

Searched Apache logs for indicators associated with the test:

```spl
index=* source="/var/log/apache2/access.log" "script" AND "%3C" AND "%3E"
```

The matching events were investigated to identify the client IP responsible for the activity.

An alert was created for the detected XSS-related log pattern.
